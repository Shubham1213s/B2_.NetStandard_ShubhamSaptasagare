Problem Statement- Employee Management System - II
Employee Management System 
1. Overview
Mini Project 2 is the continuation of Mini Project 1 — Employee Management Dashboard. In that project, you built a fully modular, service-oriented frontend using HTML5, CSS3, Bootstrap 5, JavaScript (ES6+), and jQuery, with all employee data stored in a static data.js array and all business logic distributed across seven service modules.

In this project, you will evolve that same frontend into a true full-stack application by replacing the static data layer with a real .NET 8 Web API backed by SQL Server 2022, managed through Entity Framework Core (Code First). The frontend service architecture you built in Mini Project 1 — especially the storageService.js boundary — was specifically designed so that this transition requires changes to the minimum number of files possible.

By the end of Mini Project 2, the application will support persistent employee data, real database-backed authentication, role-based access control (Admin and Viewer), server-side search, filter, sort, and pagination — all exposed through a fully documented REST API with Swagger / OpenAPI.


2. Problem Statement

Background
In Mini Project 1, XYZ Solutions was given a working frontend HR portal. However, all data lived in the browser's memory and was lost on every page refresh. The HR team cannot use a system where records disappear when the browser is closed, and the IT security team requires proper password hashing and role-based access before the system can go live.

The company now needs the frontend to be connected to a real backend system that:

•	Persists all employee records in SQL Server 2022 — data survives restarts and is shared across all users
•	Authenticates users with securely hashed passwords (BCrypt) stored in the database
•	Enforces role-based access — Admins can add, edit, and delete employees; Viewers can only read
•	Performs search, filtering, sorting, and pagination entirely in SQL Server — not in the browser
•	Exposes all functionality through a well-documented REST API (Swagger / OpenAPI)


Your Task

Build a .NET 8 Web API that serves as the backend for the Employee Management Dashboard frontend built in Mini Project 1. Connect both layers so the complete application runs end-to-end against a live SQL Server 2022 database.

You are required to:

•	Build and run the .NET 8 Web API with Entity Framework Core Code First migrations
•	Update storageService.js on the frontend to make real HTTP calls to the API (replacing in-memory array access)
•	Update authService.js to call the real login and register API endpoints
•	Implement role-based access — the API enforces it via a custom middleware; the frontend reflects it in the UI
•	Implement server-side pagination on the Employee List with page controls in the UI

5.6  Role-Based Access Control 

Role-based access is enforced via standard ASP.NET Core JWT authorization. The frontend stores the JWT after login and sends it as a Bearer token on every request.
 
•	After login, the frontend stores the user's role in-memory via authService.js 

•	[Authorize] — any authenticated user; returns 401 if token missing/expired 

•	[Authorize(Roles="Admin")] — Admin only; returns 403 for Viewer JWT 

•	[AllowAnonymous] — on auth endpoints; no token required 

•	Token signature, issuer, audience, and expiry validated automatically 

 Frontend Role UI:  After login the JWT is decoded client-side to read the role claim. Viewers see no Add, Edit, or Delete buttons. uiService.applyRoleUI() is called after every login using AuthService.isAdmin() — which checks the decoded role stored in-memory.

6.2  JWT Authentication & Authorization

Mini Project 2 uses industry-standard JSON Web Token (JWT) authentication. JWTs are self-contained tokens that carry the user's identity and role — the backend validates every request without hitting the database each time.

How JWT Works in This Project

Step 	What Happens 

1. Login 	Client sends username + password to POST /api/auth/login 

2. Token issued 	API validates credentials via BCrypt, generates a signed JWT containing { userId, username, role, expiry } and returns it to the client
 
3. Token stored 	Frontend stores the JWT in memory (authService.js). Never stored in localStorage — XSS risk 

4. Authenticated request 	Every subsequent API call sends: Authorization: Bearer  in the request header 

5. Validation 	ASP.NET Core JWT middleware validates the token signature, expiry, and claims on every request automatically — no manual header parsing 

6. Authorisation 	[Authorize(Roles="Admin")] attribute on controllers restricts endpoints — returns 401/403 automatically if token is missing or role is wrong

AuthService — Token Generation 

      private string GenerateToken(AppUser user) 

    { 
        var claims = new[] 

        { 
            new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()), 
            new Claim(ClaimTypes.Name,           user.Username), 
            new Claim(ClaimTypes.Role,           user.Role) 
        }; 
 
        var key   = new SymmetricSecurityKey( 

                        Encoding.UTF8.GetBytes(config["Jwt:Key"]!)); 

        var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256); 
 
        var token = new JwtSecurityToken( 
            issuer:             config["Jwt:Issuer"], 

            audience:           config["Jwt:Audience"], 
            claims:             claims, 

            expires:            DateTime.UtcNow.AddHours( 
                                    double.Parse(config["Jwt:ExpiryHours"] ?? "8")), 

            signingCredentials: creds); 
 
        return new JwtSecurityTokenHandler().WriteToken(token); 
    } 
}

  // storageService.js — attach token to every request 

  function _headers(withAuth = true) { 

    const headers = { "Content-Type": "application/json" }; 

    if (withAuth) { 

      const token = AuthService.getToken?.(); 

      if (token) headers["Authorization"] = `Bearer ${token}`; 

    } 

    return headers; 

  } 


Security Note:  Never store JWTs in localStorage or sessionStorage — they are vulnerable to XSS attacks. Store the token in a JavaScript variable (in-memory) as done here. The token is lost on page refresh, requiring re-login — this is the correct behaviour for a secure session.



7. Core Features to Implement

7.1  Admin Authentication (via API)

Register

•	POST /api/auth/register — accepts { username, password, role } 

•	Password hashed with BCrypt (12 rounds) before storage — never stored in plain text 

•	Duplicate username rejected with HTTP 409 Conflict and a specific error message 

•	Role must be 'Admin' or 'Viewer' — defaults to 'Viewer' if omitted  

Login
•	POST /api/auth/login — accepts { username, password } 

•	BCrypt.Verify() checks the submitted password against the stored hash 

•	Returns { success, username, role, message } on success 

•	Returns HTTP 401 with { success: false, message } on failure — does not indicate which field is wrong 

•	The frontend stores the JWT token and role in-memory via authService.js. Every subsequent API request sends Authorization: Bearer  in the header


7.2  Dashboard (Server-Computed)

•	GET /api/employees/dashboard returns all dashboard data in a single API call

•	Total Employees, Active count, Inactive count, and Total Departments — computed via SQL COUNT() and GROUP BY

•	Department Breakdown — per-department employee count and percentage, sorted alphabetically

•	Recent Employees — last 5 added, ordered by CreatedAt descending then Id descending

•	All four KPI card values update automatically after every CRUD operation (frontend re-fetches dashboard after each mutation)


7.3  Employee List with Server-Side Search, Filter, Sort, and Pagination

Search

•	Real-time search — frontend debounces 350ms then sends updated request to API

•	API performs: WHERE (FirstName + ' ' + LastName LIKE '%term%' OR Email LIKE '%term%') — case-insensitive

Filter
•	Department filter — exact match WHERE Department = @dept

•	Status filter — exact match WHERE Status = @status

•	Search + Department + Status all apply simultaneously (AND logic) in a single SQL query


Sort

•	Sort by Name (lastName asc/desc, thenBy firstName)

•	Sort by Salary (asc/desc)

•	Sort by Join Date (asc/desc)

•	Sort executes as ORDER BY in SQL — not in JavaScript


Pagination

•	API accepts page (1-based) and pageSize (default 10, max 100)

•	Skip/Take executes in SQL — only the current page's records are transferred over the network

•	Frontend renders a Bootstrap pagination bar showing page numbers, Prev and Next buttons

•	Pagination state is tracked in app.js _state object alongside search/filter/sort state

•	Record count label shows: 'Showing X–Y of Z employees'


7.4  CRUD Operations (via API)

Create — POST /api/employees

•	Client-side validation runs first (validationService.js) — prevents unnecessary API calls

•	API validates server-side (Data Annotations on EmployeeRequestDto) — returns 400 with field errors if invalid

•	If email already exists, API returns 409 Conflict — frontend maps this to an inline email field error

•	On success: 201 Created with the new employee object; frontend refreshes table and dashboard

Read — GET /api/employees/{id}

•	View button fetches the full employee record from the API by ID

•	Displayed in a read-only Bootstrap Modal — no data cached in the DOM


Update — PUT /api/employees/{id}

•	Edit button fetches the employee by ID, pre-populates the Add/Edit modal

•	Same client-side + server-side validation as Create

•	API allows the same email address to be submitted (edit without changing email) — excludes the current employee from the uniqueness check

•	On success: 200 OK with updated employee object; frontend refreshes table and dashboard

Delete — DELETE /api/employees/{id}

•	Delete button shows a confirmation modal with the employee's full name

•	On confirmation: DELETE /api/employees/{id} called; 200 OK returned on success

•	Frontend refreshes table and dashboard; navigates back to page 1 if the deleted record was the last on the current page

7.5  Navigation, Layout, and Role-Based UI

•	Fixed-top Bootstrap Navbar with application name, Dashboard and Employees links, role badge, and Logout button

•	'Add Employee' button in the Navbar — visible to Admin only (hidden for Viewer via uiService.applyRoleUI())

•	Edit and Delete action buttons per table row — visible to Admin only

•	A 'You have read-only access' notice bar displayed in the Employee List view when logged in as Viewer

•	View (eye) button is available to both Admin and Viewer

•	Logout clears the in-memory session and redirects to the Login view
